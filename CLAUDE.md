# Metro Live Map — Developer Workflow

## Git Workflow Rules

These rules apply to **every Claude Code session**. They enforce safe, reviewable development.

1. **Never commit directly to `main`.** Always work on a feature branch. Claude Code creates a git worktree + branch automatically — use it.
2. **Commit after each logical sub-task** using the format `feat:`, `fix:`, `polish:`, or `refactor:` followed by a short description.
3. **Check `.gitignore` before staging.** Never track `.env`, `scripts/*.jsonl`, `*.log`, or GTFS `.txt` files.
4. **Scope control.** Only modify files directly relevant to the current task. If a change in another file is needed, flag it to the user before editing.
5. **All merges go through a Pull Request.** The user reviews each changed file in GitHub Desktop before approving. Do not ask to bypass this.
6. **No force pushes.** Never run `git push --force` or `git reset --hard` without explicit user approval.

> Recent history is in the git log; the engineering snapshot lives in
> [`docs/STATUS.md`](docs/STATUS.md), and the (historical) launch synthesis in
> [`docs/_archive/LAUNCH-READINESS.md`](docs/_archive/LAUNCH-READINESS.md).

## Key Constraints

### Build, data & deploy

- **No build step** — all imports are relative ES module paths. The one third-party runtime lib, **MapLibre GL JS, is vendored same-origin in `vendor/maplibre-gl/`** (loaded via `<script>`/`<link>` tags in `index.html`) — NOT from a CDN. It was moved off unpkg (#245) to kill that single-point-of-failure and to drop unpkg from the CSP; a caching service worker is NOT the fix here (barred by the `sw.js` installability-only contract below). Refresh/bump via `scripts/vendor-maplibre.sh` (re-fetches the pinned dist from npm; bump `VERSION` there + the version string in `index.html` together). Same-origin ⇒ no SRI hash. The basemap tile providers (CARTO/ESRI) are still remote but keyless — see below.
- **Always edit files in the active worktree**, not directly in the main branch if a worktree is open.
- **data/ files** — Built JSON (rail-shapes.json, stops.json, trips.json, bus-routes.json, bus-destinations.json, metro-micro-zones.json) is committed; raw GTFS source files (`*.txt`, `*.zip`) are gitignored. Rebuild with `node scripts/build-shapes.cjs`.
- **Nearby-bus destination labels (`data/bus-destinations.json`)** — In the station popup's nearby-buses section, a bus row shows the **rider-facing headsign destination** ("Santa Monica"), NOT the live feed's terminus STOP name (the last stop is often an obscure intersection riders don't recognize — the original UX complaint). The source is the bus GTFS **`destination_code`** (a per-`stop_times` field, 100% populated): Metro's `trip_headsign` is present-but-EMPTY, so do NOT switch to it. The map is compact + branch-accurate: `byRouteDir` holds the dominant `destination_code` per `route|direction`; `byTrip` holds ONLY the ≈12% minority branch/short-turn trips whose destination differs (e.g. a 111 short-turning to Inglewood among mostly-LAX trips) — so every trip resolves to its TRUE destination at ~17 KB gz, zero mislabels. Resolver: `resolveBusDestination(tripId, route, dir)` in `predictions.js` = `byTrip[tripId] ?? byRouteDir[route|dir] ?? null`; `stations.js` `_resolveBusDest` falls back to the live terminus stop name only on null (e.g. a brand-new tripId after a service change, before the weekly rebuild refreshes the map). The compass cardinal still comes from the live terminus geometry. Built by `buildBusDestinationsJson()` (self-contained stream of bus `trips.txt` for direction + `stop_times.txt` for destination); reloaded on service-date rollover in `main.js` alongside trips.json.
- **GitHub Pages deployment** — serves from repo root, so `index.html` must be at root. Push to `main` auto-deploys (~60 s). The repo is **public**; live at `https://orenbj.github.io/metrolivemap/`. The `livemap.metro.net` CNAME is the LA Metro handoff target (served from `LACMTA/livemap`); the domain cutover is part of the migration — see [`docs/HANDOFF.md`](docs/HANDOFF.md) §12.3.
- **Basemaps are keyless** — CARTO (`basemaps.cartocdn.com`) and ESRI ArcGIS raster tiles, both reached via keyless tile URLs. `js/config.js` holds only tuning constants; there is **no client-visible API key** in the shipped code (no MapTiler key exists). If a keyed service is ever added, its key would be client-visible — restrict it via referrer policies in that provider's dashboard — but none is present today.
- **`sw.js` is installability-only — do NOT add caching.** The service worker exists for ONE reason: Chromium won't fire `beforeinstallprompt` (so `js/pwaInstall.js`'s "Add to home screen" banner can't appear) unless a registered SW has a `fetch` handler. It caches nothing and intercepts nothing — every request passes through to the network. This is NOT the deferred offline-mode SW; Metro Live Map is a live-data app and a cache would only ever show stale positions. The CSP allows it via `worker-src 'self' blob:`. Install affordances: a dismissible banner on Chromium (driven by the captured prompt event) and a one-off Share→Add-to-Home-Screen text hint on iOS Safari (which never fires the event); dismissal is remembered in `localStorage.mlm_pwa_install_dismissed`.
- **Tests** — `npm test` runs the Vitest suite (53 files, 1092 tests). Run after any change to ETA, snapping, or marker logic. `tests/setup.js` installs an in-memory `localStorage` shim — Node 25+ has a broken built-in `globalThis.localStorage` accessor that collides with jsdom.

### Motion model — bounded arc-glide (PR #257)

- **Trust the feed — the map TRACKS the feed, it does not second-guess it.** The marker must always end each cycle ON the latest GPS fix (via glide or teleport); the ONLY fixes that may be rejected are **geometrically, obviously wrong locations**. Two kinematic gates that used to reject *plausible* moves were REMOVED (the "trust the feed" audit): (1) `isGpsSpike`'s **rail arc-distance gate** and (2) its **predict-then-validate gate**, plus (3) the rail **catch-up rate-limit** in `_applyVelocityCorrections` and (4) the rail **implausible-implied-arc-speed teleport**. All four rejected/throttled a feed that legitimately lagged underground then jumped a stop or two forward, leaving the dot stations behind its own NEXT STOP label while prod showed the train ahead of us. **Do NOT re-add a kinematic arc/predict/rate-limit gate** — it cannot tell a real feed catch-up from a glitch, so it trades a rare false-accept for a constant false-reject that drags the whole map behind reality. What MAY still reject a fix (all "this location is impossible," not "this move is fast"): the **cross-line guard** (`isOnDifferentLine`), the **>5 km re-anchor** (still moves the marker there, just без glide), the **cold-start off-route gate** (`_isColdStartSpike`), the **snap tolerance** (a fix too far from its own polyline never snaps), and the surviving **impossible straight-line speed gate** (>`MAX_PLAUSIBLE_SPEED_MPS` ≈ 110 mph, with a near-stop bypass) — now the ONLY gate left inside `isGpsSpike`. `marker.lastVelocity` was deleted with the predict gate (it had no other reader).
- **Rail** (route with shape data): on every WS frame, `arcGlide(markerKey, fromArc, toArc, ...)` in `markers.js` glides the marker ALONG the polyline arc from its previous snapped position to the new snapped position. **Glide duration tracks the real inter-fix gap** (`(newTs - prevTs)*1000`, floored at `GLIDE_MIN_MS`, capped at `GLIDE_MAX_MS` = 60 s) so on-screen speed ≈ the vehicle's real average speed. A fixed duration caused the "zoom across the line" bug. (`GLIDE_MAX_MS` was 30 s; raised to 60 s for the GAP TAIL, not the median: the 2026-06 feed-reliability audits measured per-vehicle cadence at 5–6 s p50 / 8–11 s p90, but 1–2 % of gaps exceed 60 s — concentrated on the D Line tunnel (per-route p90 28–45 s) and rare large J Line outliers — and at 30 s those tail updates all teleported. Gap-matched duration means longer glides lag but never zoom. Do not lower the cap back based on the healthy median.)
- **Re-anchor (teleport, no glide)** ONLY on a **hard discontinuity** — a jump that can't be shown as plausible motion at ANY duration: straight-line jump > 5 km, stale reference (gap > `SPIKE_BYPASS_S`), or gap > `GLIDE_MAX_MS`. Everything else GLIDES the **full distance** from the marker's current visual arc (`_currentArc`) to the new snap, gap-matched — including a multi-station catch-up after the feed lagged. There is **no rail catch-up rate-limit and no implausible-implied-arc-speed teleport** (both removed in the "trust the feed" audit): the rate-limit throttled catch-up to ~1 station/cycle so a marker that fell behind could never close the gap on a moving train (the perpetual-lag bug), and the implied-speed teleport rejected the same legitimate catch-ups. Gap-matched duration already bounds on-screen speed, so a full-distance glide reads as fast-but-smooth motion, not a zoom. Do NOT re-add a duration cap to limit speed — `arcGlide` eases in cubically, so a long glide interrupted early by the next fix barely advances and the marker **crawls/sticks**. (Bus still re-anchors when its REAL inter-fix straight-line move exceeds `MAX_PLAUSIBLE_SPEED_MPS`, since the straight-line catch-up has no polyline to rate-limit along.) **The hard-discontinuity straight-line distance is measured against the arc the glide ACTUALLY sweeps (`current → lngLatAtArc(toArc)`), NOT just `current → _targetLng/_targetLat`** (PR #501). The two differ only when the snap target and the glide-arc (`lastSnap.arcMeters`) disagree — which is itself a bug the **STOPPED_AT arc-alignment** below prevents at the source; this is the geometric backstop that guarantees the dot can never animate a >5 km visual span no matter the cause. It is **not** the banned implied-arc-speed gate (no time/speed term — purely "this jump is too far to animate").
- **STOPPED_AT arc-alignment (PR #501).** When a vehicle is `STOPPED_AT`, `_applySnap` overrides the straight-line target (`_targetLng/_targetLat`) to the feed-DECLARED stop coords — the authoritative position. It MUST also re-anchor `marker.lastSnap` to that stop's OWN snap (`stopSnap`), because `_applyVelocityCorrections` uses `lastSnap.arcMeters` as the glide TARGET arc. If it doesn't, a momentary GPS glitch far down the polyline (observed: a Grand/LATTC A-Line train reporting the Downtown Long Beach terminus ~30 km away) leaves the straight-line target near the stop (so the >5 km gate sees a small move and GLIDES) while the glide arc points at the glitch — the marker **flies the length of the line, then hard-reanchors back** on the next clean fix. `lastSnapDeviationM` is set to the stop's own off-polyline distance (small/reliable) so the predictions.js adherence snap-quality gate still trusts it. Do NOT let `_targetLng/_targetLat` and `lastSnap.arcMeters` diverge.
- **Rotation** is a lerp from `startHeading` (prior `marker.properties.Heading`) to `targetHeading` (this frame's `computeHeading()` result, already disambiguated against the next-station bearing).
- **BRT (G/J Lines, routes 901/910/950)** use `arcGlide` along the busway polyline, same as rail. Shape data lives in `data/rail-shapes.json` (built alongside rail routes by `build-shapes.cjs`). Snap threshold is `BRT_SNAP_MAX_M = 150 m` (vs the generic `BUS_SNAP_MAX_M = 75 m`) — the dedicated busway has rail-class guideway fidelity. GPS > 150 m from the polyline (detour) falls through to straight-line. `isBrtRoute()` in `utils.js` identifies these routes; `isBusRoute()` still returns `true` for them so SVG icons remain bus-shaped (rounded square, not circle).
- **Station click layers** — Two invisible MapLibre circle layers partition station dots by zoom. `metro-stations-click` (minzoom `STATION_CLICK_MINZOOM` = 10) handles all rail stations and named BRT busway stops (Harbor Transitway, El Monte Station, etc.). `metro-stations-click-jline` (minzoom `JLINE_STOP_CLICK_MINZOOM` = 14) handles J Line street-running intersection stops (Pacific / 17th, Figueroa / Pico, etc.) whose Metro basemap dots only appear at high zoom. The split is computed by `_isJLineOnly(g)` in `stations.js`, which checks the `buswayStation` flag set by `addToRegistry` from the raw stop name (any name containing "Transitway", "Busway", "Transit Center", or "Station" is classified as BRT infrastructure, not street-running).
- **Buses** (non-BRT, no shape data) use `animateMarker` straight-line lat/lng glide at the same gap-matched duration; re-anchor when implied straight-line speed exceeds `MAX_PLAUSIBLE_SPEED_MPS`.
- **Cold start** spawns the marker at its snapped GPS position with no glide. When a new WS frame arrives mid-glide, the in-flight glide is cancelled and a fresh one starts from the marker's current visual position via `_currentArc` (smooth handoff).
- **Critical invariant:** the marker is bound between two known GPS positions — it **NEVER moves past the latest GPS fix**, cannot extrapolate, cannot overshoot, cannot disagree with the popup label. **One sanctioned exception: the underground stop-lag re-anchor** (below) snaps a *frozen* marker forward to a feed-**declared** stop. That is a discrete jump to an authoritative feed-reported position bounded by the stop sequence — NOT extrapolation/DR (no continuous projection, no `speedFactor`); it *removes* the marker-disagrees-with-its-own-label case rather than creating it.
- **Vehicle motion is NOT gated by `prefers-reduced-motion`** (PR #267). It conveys real-world movement (WCAG-2.3.3-exempt "essential motion"). Gating it turned every vehicle into a teleport for OS-level Reduce-Motion users — do not re-add the gate. Decorative transitions (map `flyTo`, popup fades) may still honor reduced-motion.
- **DR is gone — do NOT bring it back.** DR and every extrapolation-compensating mitigation (declared-stop clamp, STOPPED_AT misfire detection, `stopIdLag` counter, `_effectiveNextStopId` override, station-popup past-target guard) were removed in PR #257. Do NOT re-introduce a `speedFactor`, a `_drCurrentArc`, or any code that projects the marker past its last GPS fix.
- **Stop-lag GPS-refresh override (`STOP_LAG_REANCHOR_STOPS` = 2).** Symptom: a rail marker sits stations behind its own NEXT STOP popup label (most visibly on the downtown tunnel — Regional Connector / B/D subway). **Key diagnostic: a page refresh moves the dot to the correct spot.** A fresh marker skips the spike check (`isFirstFix`) and snaps straight to the feed position — so the feed *carries* the correct position; the long-running marker's spike gate / jitter-hold are wrongly **rejecting or holding the legitimate forward move** (the feed lags then jumps; the arc gate rejects the jump as a spike, and interleaved no-move frames keep resetting the `SPIKE_REANCHOR_STREAK` so the hatch never fires). The fix mirrors what a refresh does: `_stopLagFromDeclared(marker, vehicle, marker._currentArc)` in `markers.js` measures how many whole stops the feed-declared next/current stop is ahead of the marker's **VISIBLE arc** (`_currentArc` — the user-visible symptom, NOT the GPS snap). When ≥ `STOP_LAG_REANCHOR_STOPS`, `updateExistingMarker` sets `forceGpsRefresh`, which passes a `forcePull=true` flag to `_applyVelocityCorrections` (the 7th param, formerly named `forceReanchor`) and bypasses `isGpsSpike` (alongside `!isFirstFix && !isStaleRef && !forceReanchor`). **NOTE: after the "trust the feed" audit removed the arc/predict spike gates and the catch-up rate-limit, `forceGpsRefresh` is mostly vestigial** — a normal accepted frame now ALSO glides the full distance to the snap, so the marker no longer needs a special override to escape a gate that's gone. `forcePull`'s only remaining effect is bypassing the **jitter-hold** (so a stop-lag correction advances even if the per-cycle arc delta would otherwise read as sub-deadband). **`forcePull` GLIDES the full distance, it does not teleport** — only a hard discontinuity (`distMeters > 5000`, `isStaleRef`, gap > `GLIDE_MAX_MS`) teleports even under `forcePull`. On **bus** (no polyline) `forcePull` teleports, but stop-lag is rail-only (`_stopLagFromDeclared` requires `hasShapeData`) so that path is defensive. It self-clears as `_currentArc` advances past the threshold. Measuring from the VISIBLE arc is deliberate — it keys off "the dot the rider sees is N stations behind the label." A normal IN_TRANSIT_TO marker is only 1 stop ahead of itself, so 2+ is a genuine multi-station lag. Stop matching uses `findIdx` (fuzzy, suffix-aware); routes with no/unreliable arc data return null → no override (safe fallback). This **moves the marker TO the latest GPS fix, never past it** — it does not violate the no-extrapolation invariant (it re-applies a real feed position the gates were dropping, and the catch-up cap keeps the visual speed bounded). Counter: `stopLagReanchor` (a *correction* count, not a drop) in `feedStats.js`. (An earlier PR #438 attempt re-anchored to the declared *stop* and ran only on accepted frames, *after* the spike gate — so rejected forward fixes never reached it; it didn't work and was replaced by this override.)
- **Spike re-anchor escape hatch (`SPIKE_REANCHOR_STREAK` = 3, PR #283) — now largely vestigial.** Originally: a tunnel-emergence fix landed far ahead of the frozen last-surface snap, `isGpsSpike` rejected it as an arc/speed spike, and the marker stayed frozen until a page refresh. After the "trust the feed" audit removed the arc and predict gates, the surviving impossible-speed gate has a near-stop bypass, so tunnel-emergence fixes are no longer rejected and `_consecutiveSpikes` rarely climbs. The hatch (`updateExistingMarker` counts consecutive rejections on `marker._consecutiveSpikes`; after `SPIKE_REANCHOR_STREAK` in a row it force-accepts the next fix and resets the streak) is kept as a defensive backstop for a *sustained* impossible-speed streak, but it almost never fires now.
- **`isGpsSpike` elapsed is measured from `_lastAcceptedTs`, not the passed `prevTs`.** `prevTs` is `marker.timestamp`, which is bumped on every *rejected* frame, but the reference position (`marker.lastSnap`) only advances on *acceptance*. Pairing a one-cycle time budget with a multi-cycle-stale reference made a multi-cycle catch-up after a rejection look faster than the impossible-speed cap. Measuring `elapsed` from the last *accepted* fix makes the surviving speed budget scale with the real time the reference has been held; steady-state is unchanged (`_lastAcceptedTs === prevTs` when nothing was rejected). (The arc-distance and predict gates this note also covered were removed in the "trust the feed" audit — only the impossible-speed gate remains.) When a spike streak ends, `smoothedSpeed` is reseeded so the kinematic ETA doesn't carry a stale pre-streak speed.
- **Cross-line spike guard (`isOnDifferentLine`) — "a vehicle cannot be on a different line."** A purely *geometric* reject — exactly the kind of "logically unreasonable location" the "trust the feed" audit kept while removing the kinematic gates: when a rail fix snaps > the route's snap tolerance from its OWN polyline (off its line) AND snaps within tolerance of a DIFFERENT, non-interlined rail line's polyline (and closer to it than to its own), the fix is dropped — it would draw the marker on the wrong line. **Interlined pairs share track and are exempt:** A(801)↔E(804) (Regional Connector), B(802)↔D(805) (Wilshire/Vermont–Union Station subway), C(803)↔K(807) (Aviation/Century–Redondo). Only the six revenue rail lines are checked (BRT 901/910/950 and the inactive 806 are excluded); buses return false immediately. **This gate SUPERSEDES every force bypass** (`forceReanchor` / `forceGpsRefresh` / `isStaleRef`) **and covers FIRST fixes too** — it runs on a marker's first update (no `isFirstFix` skip) and on COLD START (before `createNewMarker`), so a mis-tagged vehicle never spawns or renders on another line even once: a forced pull, streak escape-hatch, or fresh marker must never land on another line's track. On reject it holds position WITHOUT advancing `marker.timestamp`/`_lastAcceptedTs`, so a *persistently* mis-tagged vehicle (wrong `route_code`) ages out via the freshness tier / cleanup TTL instead of being rendered on the wrong alignment. Cost-bounded: the multi-line scan runs ONLY when the own-line snap already failed (a rare off-route fix), so steady-state cost is one own-line snap. Counter: `crossLineSpike` in `feedStats.js`. The guard exists *because* the spike protection was loosened (gap-matched glide + stop-lag forcePull + streak hatch) — it re-adds a hard floor the kinematic gates no longer guarantee. 
- **Reject-path glide contract, bounded backward release, and the glide clock (marker-accuracy batch G2).** Three refinements that keep the dot ON the feed without re-adding kinematic gates: (1) **A rejected frame (cross-line / spike) does NOT cancel the in-flight glide** — the marker keeps moving to the last ACCEPTED fix (cancelling stranded it mid-glide, parked between fixes); only the glide's completion callback is dropped (so the old frame can't re-stamp `marker.timestamp` after the reject path bumped it), and the cancel happens on the ACCEPT path instead, right before the new glide starts. Do not move `_cancelGlide` back to the top of `updateExistingMarker`. (2) **The rail jitter-hold's backward side is BOUNDED** (`POS_JITTER_BACKWARD_RELEASE_M` = 75 m × `POS_JITTER_BACKWARD_STREAK` = 2 consecutive accepted fixes → glide back; counter `backwardRelease`). Unbounded, backward motion could never render: real reversals (single-tracking) froze the dot for minutes, and an accepted forward GPS spike became *sticky* — every corrective backward fix held, the dot parked AHEAD of the feed in green, the one direction "never past the latest fix" forbids. The release is feed-tracking, not a kinematic gate: it glides to an *accepted* fix. Sub-75 m backward noise stays held forever; any non-large-backward frame breaks the streak. (3) **Glide duration and the `GLIDE_MAX_MS` teleport test measure the gap from `_lastAcceptedTs`** (the fix actually being interpolated from), NOT `marker.timestamp` (bumped on rejected frames) — post-rejection catch-ups animate at real speed instead of K×, and a 70 s real gap split by a rejected frame honestly teleports. Same reference the `isGpsSpike` budget already uses; steady state identical. Also: the easing is now TRUE cubic-in-out (`1 − (−2t+2)³/2` second half — it was quadratic-out, a 33 % instantaneous mid-glide speed drop on every glide; pinned by a velocity-continuity test in `tests/glide-invariant.test.js`).

### Hidden-tab feed suspend (Batch D1)

- **Both live WS feeds CLOSE after the tab is hidden `WS_HIDDEN_SUSPEND_MS` (60 s), and re-open fresh on return.** While hidden the feeds otherwise receive + parse a firehose nobody is watching — `js/api.js` (vehicle positions, ~170 frames/s) at least buffers latest-per-vehicle and skips rendering, but `js/tripUpdates.js` (~850 frames/s on bus) processed EVERY frame. Suspending stops the radio + CPU cost entirely. **The two modules suspend INDEPENDENTLY** — each arms its own grace timer in its own `visibilitychange` handler and closes its own sockets; there is no cross-module coordinator (deliberate — they already duplicate the WS lifecycle). Alerts are HTTP-polled via `setVisibleInterval` and already pause, so they're out of scope.
- **The 60 s grace is what makes quick tab-flips free** — a glance away under 60 s never suspends (the existing hidden-tab buffer covers that window); only real backgrounding pays the reconnect-on-return. Don't drop the grace to 0 (thrashes a full snapshot reconnect on every alt-tab) — it was a deliberate UX call.
- **Suspend mechanics (mirror in both modules):** a `_suspendClose` flag on each socket + a module-level `_feedsSuspended` gate make `onclose` tear down its timers but skip BOTH the offline toast and the reconnect schedule; in-flight reconnect timers are cancelled. **`onclose` must keep this guard** (`if (socket._suspendClose || _feedsSuspended) return;` right after the `clearInterval`/`clearTimeout` cleanup) — without it a suspended close would immediately reconnect and defeat the whole feature. Resume re-opens every known feed (`api.js` tracks `_feedUrls`; `tripUpdates.js` re-`connect`s its two fixed URLs), Metro re-sends a full snapshot, and the `>GLIDE_MAX_MS` blackout makes markers **hard-reanchor** to their fresh fixes (counter `hardReanchor`) rather than fake-gliding across the gap — exactly the no-extrapolation contract. `api.js` drops its hidden-tab buffer on suspend (those frames are stale by resume). Tests: `tests/api.suspend.test.js` (grace timer, suspended-close-no-reconnect/no-offline, resume re-opens; register the visibility handler ONCE per describe or stacked listeners leak timers across tests).

### Feed-data correctness (silent gates — the only difference is the absence of wrong data)

- **Reject future timestamps** — `js/api.js` `processAndUpdate` drops frames timestamped more than `FUTURE_TS_GRACE_MS` (5 s) in the future. A future ts passes `Number.isFinite()` and collapses every downstream `now - ts` age check to 0 (= "fresh"). Tracked via the `futureTs` drop counter.
- **CANCELED trips / SKIPPED stops** — `js/tripUpdates.js` early-returns when `trip.scheduleRelationship === 'CANCELED'` (canceled trips never populate `masterArrivalsData`); per stop, `stu.scheduleRelationship === 'SKIPPED'` omits that single stop while siblings keep their pills.
- **`vehicleNoArrivalMatch` counter** — reverse of `ghostArrivals`. Fires in `getVehicleEtaSecs` when a live IN_TRANSIT_TO marker has a finite `stopId` and trip_updates has predictions at that stop but none matching THIS vehicle's `vehicle_id`/`trip_id` (popup falls back to schedule ETA). Episode-gated via `marker._noArrivalMatchRecorded`, cleared on stopId advance; STOPPED_AT excluded.
- **Cross-midnight trip preservation** — `js/serviceDate.js` `_preserveActiveTrips(oldTrips, newTrips, markers)` (called from `_reloadGtfsData` in `main.js`) merges any still-active tripId that exists in the OLD `masterTripsData` but not the freshly-fetched JSON, so owl trips keep their static context (terminus, stop sequence, `isLast`) until they terminate. Safe because Metro's tripIds are unique per service date (never recycled).
- **Synthetic schedule-based vehicleIds** — `scanGhostArrivals` skips vehicleIds ending in `_schedBasedVehicle` (Metro publishes schedule-derived predictions for not-yet-assigned trips; ~1,484 in one 20-min capture would otherwise swamp the genuine-ghost signal).
- **ID String-cast at the feed boundary** — `js/api.js` String-casts every feed-derived ID (`vehicle_id`, `trip_id`, `stopId`, `route_code`) before placing it on `feature.properties`; the trip_updates side casts too. Downstream does strict-equality lookups, and a number-vs-string mismatch silently drops cross-feed matches. Most visible failure mode: `isBusRoute('910')` — a numeric `910` would route the whole bus fleet through rail physics with no log. Cast new IDs at the api.js boundary, not at every reader.

### Observability & CI

- **Marker correction/event counters (`feedStats.js` `_markerStats`, marker-accuracy batch G4)** — non-drop counts the audit found had no production trace, so their rates were unmeasurable. `hardReanchor` (a teleport on a hard discontinuity — >5 km / stale ref / gap > `GLIDE_MAX_MS`; CLAUDE.md claims ~1–2 % of gaps — this checks it), `streakForceAccept` (the `SPIKE_REANCHOR_STREAK` escape hatch fired), `declaredAnchor` (glided to the feed-declared STOPPED_AT stop arc), `backwardRelease` (bounded backward jitter-release, G2). `stopLagReanchor` is **episode-gated** (one per transition into the lagging state via `marker._stopLagEpisode`, NOT per-frame — under a frozen GPS the condition holds every frame, which turned a correction COUNT into a duration measure). All print in the `corrections(...)` segment of the `_report` console line and land in the ring; keep `scripts/analyze-ring.js` `MARKER_KEYS` in lockstep.
- **Clock-skew blank-map alarm (`feedStats.js` `_report`)** — a device clock ≥ `FUTURE_TS_GRACE_MS` SLOW makes every legitimate frame look future-stamped → 100 % `futureTs` drops → an empty map with no on-screen reason (the only total-failure mode the feed audit found). `_report` aggregates `futureTs / received` across ALL feeds (a slow client clock hits all of them; an upstream serializer bug hits one) and `console.warn`s ONCE per session (`_clockSkewWarned`) when the fraction ≥ 50 % on ≥ 20 received. Diagnostic only — the gate itself is unchanged.
- **localStorage feedStats ring** — each `_report()` tick with activity appends one snapshot to `localStorage.feedStatsRing` (max `FEED_STATS_RING_MAX` = 1440 = 24 h). Shape: `{ t, feeds: { [shortName]: { rcv, acc, drops, cadence } }, markers: {…}, ghosts }`. Inspect via `JSON.parse(localStorage.feedStatsRing)`. Helpers in `js/feedStats.js`: `readFeedStatsRing()`, `clearFeedStatsRing()`, `FEED_STATS_RING_KEY`. Best-effort — quota/parse errors are swallowed; silent intervals are skipped. The headless harness appends a tagged ring row (`row.__kind === 'feedStatsRing'`) at the tail of its JSONL artifact.
- **Scheduled feed-reliability audit** — `.github/workflows/feed-reliability.yml` runs `scripts/audit-feeds.js` against the live Metro WS feeds (crons **active** — public repo, unlimited Actions minutes; manual `workflow_dispatch` also works). **Source of truth for "does Metro actually populate field X?"** — before wiring up any optional GTFS-RT field (`occupancyStatus`, `arrival.uncertainty`, `tripUpdate.delay`, `position.bearing`, …) consult the latest report's `vehicleFields`/`stuFields` block. Decision rule: ≥30 % nonNull → wire it up; 5–30 % → document partial coverage; <5 % → skip. Local: `node scripts/audit-feeds.js --duration=30m --out=/tmp/r.json`.
- **`rebuild-gtfs.yml`** — the weekly Mon 09:00 UTC auto-rebuild has an `if: failure()` fallback that files an issue under label `gtfs-rebuild-failure` when PR creation is blocked (repo setting "Allow GitHub Actions to create and approve pull requests" off → HTTP 403), so the rebuild requirement is never silently dropped.

### UI behavior & marker lifecycle

- **Vehicle freshness tiers** — `getFreshnessTier(marker, nowSec)` in `js/freshness.js` (shared by `markers.js` and `ui.js`) is the single source of truth for per-vehicle VISUAL state. Three tiers → (marker opacity, popup-dot color):
  - `live`    (age < 90 s)  → 1.0 / green
  - `stale`   (age < 300 s) → 0.5 / gray
  - `expired` (age ≥ 300 s) → fade-out & remove

  **`getFreshnessTier` reads `marker._lastAcceptedWallMs` (the RECEIPT clock) — the SAME clock the popup footer dot + "Xs ago" use, so marker opacity, popup dot, and "Xs ago" never disagree.** This unified them (PR #511-era audit): they used to split — opacity on `_lastAcceptedTs` (the GPS fix's own timestamp), popup on `_lastAcceptedWallMs` (wall-clock receipt) — which let a feed-lagged train fade gray on the map while its popup still read green "45s ago" (the feed's GPS timestamp lags ~40s+ in the downtown tunnel). Receipt time keeps the anti-spike safety that motivated the old `_lastAcceptedTs` choice: it advances ONLY on accepted fixes (a spike-rejection streak, or frozen-GPS `olderTs` rejections, never reset it), so a stuck/bad-GPS marker still ages to gray/expired; the only change is that a live train on a lagging feed stays green (correct — it IS live). Do NOT drive the visual tier from `marker.timestamp` (bumped on rejected frames). **Separately, predictions' OWN freshness gate (`getVehicleEtaSecs` / station-board TTL) still reads `_lastAcceptedTs`** — that's a data-staleness question (is the trusted position fresh enough to compute an ETA), not a visual one; keep it on the GPS-fix clock. `marker.timestamp` remains for `isStaleRef`, the cleanup hard-TTL, and feedStats age tracking.

  Constants: `FRESH_STALE_S` (90 s), `FRESH_EXPIRE_S` (300 s). Decoupled from `SPIKE_BYPASS_S` (120 s, spike-rejection) and `VEHICLE_MARKER_TTL_S` (180 s, ETA filter) — those are algorithmic gates, not visual. (`FRESH_LIVE_S` = 30 s in config.js is a separate predictions.js speed-freshness gate, unrelated to the tier model.)
- **`_openVehiclePopups` counter & marker-remove contract** — `markers.js` tracks open vehicle popups (incremented in `popup.on('open')`, decremented on `'close'`) so the per-second popup-age refresh ticks short-circuit on `=== 0`. **MapLibre's `marker.remove()` does not reliably fire `'close'`**, so every marker-removal call site MUST call `marker.getPopup()?.remove()` first or the counter drifts upward. The glide helpers use a callback (`marker._animateMarkerOnComplete`), not Promises — cancellation in `updateExistingMarker` deletes the flag so a cancelled glide can't fire `updateMarkerTimestamp` after the new GPS was applied.
- **Single active popup (`js/popups.js`)** — at most ONE popup is open at a time across the four independent owners: vehicle markers (`markers.js`), station arrivals (`stations.js`), Metro Bike Share (`bikeshare.js`), Metro Micro (`microzones.js`). Each owner, immediately after showing its popup, calls `setActivePopup(itsCanonicalCloseFn)`, which closes the previously-active popup **via that popup's own close fn** — NOT a bare `popup.remove()` — so per-type teardown runs (e.g. the station closer also clears vehicle highlights + restores focus). Each owner also calls `notifyPopupClosed(itsCloseFn)` from its `'close'` handler so the registry pointer drops on ×/map-click/Escape. The close fn must be a **stable reference** (a module-level fn like `closeStationPopup`/`_closeActivePopup`/`_closeMicroPopup`, or a per-popup closure reused in BOTH calls) so the identity guard works. **Any new popup type MUST register the same way** or it re-introduces the overlapping-tooltip bug. `popups.js` is a leaf module (no imports) to avoid the markers⇄stations cycle.
- **Startup auto-locate popup** — `autoLocate(isStartup=true)` must wait for BOTH `map.once('idle')` AND the `loadingDone` promise from `ui.js` (resolved by `removeLoadingScreen` on the 2nd WS connect or a 15 s fallback) before opening the nearest-station popup, or it renders over the still-visible loading splash. The locate-BUTTON path (`isStartup=false`) skips the splash gate.
- **ETA-source debug tag** — set `localStorage.mlm_debug_eta = '1'` (then reopen a vehicle popup) to render a `[RT]`/`[calc]` tag next to the next-stop ETA. `getVehicleEtaSecs` records the tier on `marker._etaSource` (`'gtfs-rt' | 'calc' | 'stopped' | 'none'`); `getPopupHTML` renders it only when the flag is set. Off by default, zero rider-facing effect.
- **Map is locked north-up (no rotation, no pitch)** — `initMap` (`map.js`) sets `dragRotate: false` + `touchPitch: false`, calls `map.touchZoomRotate.disableRotation()` (keeps pinch-zoom, drops the twist) and `map.keyboard.disableRotation()`, and adds the `NavigationControl` with `showCompass: false`. This is deliberate for a 2D transit OVERVIEW map: rotation on a phone is almost always accidental (a pinch that twists), disorients riders, and **misaligns every north-up overlay** — boarding/departure pills, directional arrows, the 8-cardinal boarding-slot geometry. Because bearing is always 0, no overlay needs `getBearing()` counter-rotation (there is none in the codebase — keep it that way). Do NOT re-add the compass or re-enable `dragRotate`/rotation without also making all those overlays bearing-aware.

### A11y, privacy & security

- **Non-text contrast for low-luminance route colors** — E (#fdb913), K (#e56db1), J (#adb8bf) fail WCAG 1.4.11 (3:1) on white; the brand palette is preserved. Mitigation: the **numeric vehicle count rendered as text** beside every legend bar carries the data, so the fill is a supplementary magnitude cue (the 1.4.11 "required to understand the content" exception) and the legend is never color-only. (A per-route `.bar-fill` outline was tried — #238 on every bar, #271 scoped to E/K/J — but removed: an outline on only some bars reads as inconsistent. Do NOT re-add a per-route outline; a uniform edge on ALL `.bar-fill` is the only acceptable form if one is ever wanted.) `.boarding-badge` gets a 2 px border + inset light outline in dark mode; `.pv2-dot` carries `role="img"` + `aria-label`. `tests/route-color-contrast.test.js` pins every route hex's contrast — if a route color or the KNOWN_FAILING set changes, update the test.
- **Focus trap + skip-link** — the alerts panel modal traps Tab/Shift+Tab at its boundaries (document-level keydown gated on `isAlertsPanelOpen()`); `openAlertsPanel` snapshots `document.activeElement` and `closeAlertsPanel` restores it. The skip-link targets `#station-search` (focusable), not the bare `#map`.
- **A11y landmarks + ARIA** — `<main id="map">` wraps the map; `<header role="search">` wraps the search bar. Search input has `aria-describedby`/`-controls`/`-expanded`; `#alerts-tab-announce` is a polite live-region written by `switchAlertsTab`; station popup name is `<h3>`.
- **No client analytics** — GTM/GA4 removed entirely (visitor IP to Google without consent = GDPR gap). Re-introducing analytics requires a proper consent flow AND re-adding `googletagmanager.com` + `google-analytics.com` to the CSP — see the CSP comment in `index.html`.
- **Clickjacking guard is a JS frame-buster, NOT `frame-ancestors`** — `frame-ancestors` is ignored when delivered via `<meta>` (needs an HTTP header GitHub Pages can't set). The guard is a synchronous inline frame-buster in `index.html` `<head>`. If the deployment ever moves behind a host that CAN set headers, prefer `frame-ancestors 'self'` + `X-Frame-Options: SAMEORIGIN` as headers.

### Misc

- **Translation** — page is `<html lang="en">` and relies on each browser's built-in translate feature (~100 languages, translates alert prose too). The in-app en/es dictionary (`js/i18n.js`) was retired — **do NOT re-introduce a per-string translation table.** Alert bodies stay wrapped `<p lang="en">` so translators/screen-readers identify the source language.
- **Rollback runbook** — [`docs/ROLLBACK.md`](docs/ROLLBACK.md) is the canonical "main is broken in production" recovery doc: severity triage, immediate revert via `git revert` (no force-push, rule-6 compliant), fix-forward, and restore-from-known-good-SHA (gated on explicit user approval).

## Cross-Module Globals (`window.*`)

The app deliberately exposes shared state on `window` instead of routing every read through explicit imports. This is a conscious choice for a no-build SPA — it keeps modules small and avoids circular-import gymnastics. Treat these as the public API surface between modules; **do not refactor them away without a plan.**

| Global                                       | Owner module           | Shape                                  |
|----------------------------------------------|------------------------|----------------------------------------|
| `window.map`                                 | map.js (assigned in main.js) | MapLibre map instance                  |
| `window.masterStopsData`                     | main.js (loads)        | Object<stopId, {lat,lon,name,…}>       |
| `window.masterTripsData`                     | main.js (loads)        | Object<tripId, {…}>                    |
| `window.masterBusRoutes`                     | main.js (loads)        | Object<routeId, {…}>                   |
| `window.masterBusDestinations`               | main.js (loads)        | { dests[], byRouteDir, byTrip }        |
| `window.masterArrivalsData`                  | tripUpdates.js         | Map<stopId, Arrival[]>                 |
| `window.masterAlertsData`                    | alerts.js              | Map<routeCode, Alert[]>                |
| `window.masterStopAlertsData`                | alerts.js              | Map<stopId, Alert[]>                   |
| `window.masterStopAccessibilityAlertsData`   | alerts.js              | Map<stopId, AccessibilityAlert[]>      |
| `window.masterBikeStations`                  | bikeshare.js           | Map<stationId, {…}>                    |
| `window.vehicleMarkers`                      | markers.js             | Object<tripId, MapLibre marker>        |
| `window.stationGroups`                       | stations.js            | Array<MergedGroup>                     |

`tripTerminusByTripId` used to live on `window` too; PR #151 removed the mirror —
production consumers (`stations.js`, `predictions.js`) now import the named binding
from `tripUpdates.js` directly. The single-access-path invariant prevents future
writers from leaving one site reading stale state.

**Debug-only hooks** (not part of the contract — fine to omit when refactoring):
- `window.__visRegistrySize` — exposed by `utils.js` for inspecting the `setVisibleInterval` registry size.

### Cross-module callbacks (`window.__`)

`stations.js` exposes three function hooks on `window` so other modules can drive station-popup behavior **without importing `stations.js`** (which would create an init-order cycle through `main.js`). All three are set once at module load:

| Hook                                | Set by      | Called by      | Purpose                                                          |
|-------------------------------------|-------------|----------------|------------------------------------------------------------------|
| `window.__openStationByGroup`       | stations.js | bikeshare.js   | Open the station arrivals popup for a merged stop group          |
| `window.__hoverStationByGroup`      | stations.js | bikeshare.js   | Soft-preview hover (no pin) used when the user hovers a bike pin |
| `window.__closeStationIfUnpinned`   | stations.js | bikeshare.js   | Dismiss an unpinned hover-preview when the user leaves the pin   |

These are intentional inversion-of-control hooks — keep the `__` prefix and the optional-chained `?.()` call pattern so they fail silently if `stations.js` hasn't initialized yet.
