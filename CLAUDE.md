# Metro Live Map — Developer Workflow

## Git Workflow Rules

These rules apply to **every Claude Code session**. They enforce safe, reviewable development.

1. **Never commit directly to `main`.** Always work on a feature branch. Claude Code creates a git worktree + branch automatically — use it.
2. **Commit after each logical sub-task** using the format `feat:`, `fix:`, `polish:`, or `refactor:` followed by a short description.
3. **Check `.gitignore` before staging.** Never track `.env`, `scripts/*.jsonl`, `*.log`, or GTFS `.txt` files.
4. **Scope control.** Only modify files directly relevant to the current task. If a change in another file is needed, flag it to the user before editing.
5. **All merges go through a Pull Request.** The user reviews each changed file in GitHub Desktop before approving. Do not ask to bypass this.
6. **No force pushes.** Never run `git push --force` or `git reset --hard` without explicit user approval.

## Key Constraints

- **No build step** — all imports are relative ES module paths. CDN libs loaded via `<script>` tags in `index.html`.
- **Always edit files in the active worktree**, not directly in the main branch if a worktree is open.
- **data/ files** — Built JSON files (rail-shapes.json, stops.json, trips.json, bus-routes.json, metro-micro-zones.json) are committed; raw GTFS source files (*.txt, *.zip) are gitignored.
- **GitHub Pages deployment** — serves from repo root. `index.html` must be at root. Push to `main` auto-deploys. Custom domain `livemap.metro.net` in CNAME is pending DNS.
- **API keys** in `config.js` are client-visible; restrict via referrer policies in ESRI/MapTiler dashboards.
- **Tests** — `npm test` runs the Vitest suite (~27 files, ~623 tests covering predictions, snap, heading, spike rejection, DR animation, marker lifecycle, calibration, adherence, boarding merging, trip updates, the WS API, alerts ingestion + normalization, bus-bridge detection, build-shapes logic, intersection lookup, freshness tiers, service-date rollover, pure utility math). Run after any change to ETA, snapping, or marker logic. Test environment uses a small in-memory localStorage shim in `tests/setup.js` (Node 25+ has a broken built-in `globalThis.localStorage` accessor that collides with jsdom).
- **DR motion model** — `markers.js` runs a continuous rAF integrator (`_arcTick`) that advances **rail** markers along their polyline each frame. `startDeadReckoning` is an idempotent param-refresh, never cancels/restarts the loop. Speed transitions use exponential damping (τ = `DR_SPEED_GLIDE_TAU_S`). **Buses** (no shape data) no longer run a continuous integrator — bearing-DR was retired (PR #226) because it projected blindly along the last GPS heading and routinely cut corners through buildings on turning streets. Bus motion is now the per-WS-frame `animateMarker` glide (~1 s ease from current visual position to new GPS); marker sits at last GPS between fixes (typically 5-15 s) — honest about what we know rather than guessing. Vehicle motion is intentionally **not** gated by `prefers-reduced-motion` — it is functional (mirrors real-world movement), not decorative animation.
- **Declared-stop clamp invariant (PR #210, narrowed 2026-05-21)** — a vehicle marker MUST NEVER visually pass a stop **while the popup says the vehicle is AT that stop**. Originally the clamp also fired for `IN_TRANSIT_TO` ("Next stop"), but the feed's `stopId` routinely lags a stop or two behind a moving train, so clamping in-transit markers yanked moving trains backward onto platforms they had already left ("too aggressively pulled to the next stop", user feedback 2026-05-21). The clamp is therefore **gated to `STOPPED_AT` only** (popup label "At stop"); `IN_TRANSIT_TO` markers follow GPS freely. Enforced in `_applySnap` (markers.js): when the vehicle is `STOPPED_AT` and `snap.arcMeters` projects past the arc of the declared `props.stopId`, snap.arcMeters is pulled back to that arc and `snappedLng/Lat` are re-projected via `lngLatAtArc`. `startDeadReckoning` uses the declared stop's arc as `_drStopArcCap` for `STOPPED_AT` vehicles; for `IN_TRANSIT_TO` (and when no stopId is available) it falls back to the legacy scan-first-ahead, which caps the DR coast at the next physical stop **ahead** of the marker — it never yanks a marker backward against a GPS fix. On warm DR, `_drCurrentArc` is also clamped to whatever `_drStopArcCap` resolves to. Helper: `_declaredStopArcCap(props, isMisfire = false)` returns `{ arc, ascends }` (or `null` when not `STOPPED_AT`, `isMisfire === true`, no stopId, or stop not cached) — `ascends` is driven by adjacent-arc comparison so the direction check works regardless of `direction_id` (dir=1 trips have descending cache.arcMeters). The `isMisfire` gate (2026-05-26) prevents the clamp from pinning a STOPPED_AT-misfiring vehicle (feed says "At stop" but observed motion proves otherwise) at the stale stop arc — without it, the misfire bypass in DR halt was silently defeated by the clamp re-imposing the cap. Counter: `feedStats._markerStats.declaredStopClamp` increments per frame the clamp engages — now only around `STOPPED_AT` station passes; a baseline near zero is healthy. Note: Metro's feed only emits `STOPPED_AT` and `IN_TRANSIT_TO` (never `INCOMING_AT`/"Arriving"), so the gate is effectively "At stop" vs "Next stop". **Trade-off, re-decided 2026-05-21**: the pre-narrowing clamp froze a moving train at its declared stop whenever the feed's stopId lagged — honest to the popup text but visually a "stuck train". The narrowed clamp lets in-transit markers follow GPS (so a marker can briefly sit past a stop the popup still calls "Next" when the stopId is stale) and only pins the marker when the popup actually says "At stop". Smoothness for moving trains now wins over strict popup-text consistency; the hard pin is reserved for the AT-stop case where the marker and label must agree.
- **STOPPED_AT misfire detection (2026-05-26)** — `_isStoppedAtMisfire(marker, speed, ts)` in `markers.js` fires when the feed claims `STOPPED_AT` but either (1) reported speed > `STOPPED_AT_MISFIRE_SPEED_MPS` (1.0 m/s) — a clearly-moving vehicle being mislabeled, or (2) the status has been `STOPPED_AT` for > `STOPPED_AT_MISFIRE_AGE_S` AND the snap arc has drifted by > `STOPPED_AT_MISFIRE_ARC_DELTA_M`. The result is written to `marker.properties._misfireOverride` in `_applySnap` and consumed everywhere via `isEffectivelyStopped` (see next bullet). **Speed-source convention**: `_applySnap` reads `vehicle.properties.position_speed` (current frame's raw feed value — `_applyVelocityCorrections` hasn't run yet); `startDeadReckoning` reads `marker.properties.smoothedSpeed` (now the freshly-EWMA'd value); `createNewMarker` also reads `position_speed` directly for cold-start misfire detection, since there is no prior `smoothedSpeed` to EWMA against on the first frame. Both runtime paths consume the same incoming reading, just through different stages of the per-frame propagation pipeline. Counter: `feedStats._markerStats.stoppedAtMisfire` increments once per misfire episode (cleared when the feed transitions out of `STOPPED_AT`).
- **stopIdLag observability counter (2026-05-26)** — pure measurement. In `_applySnap`, when the feed reports `IN_TRANSIT_TO` and the post-snap `arcMeters` has already moved past the declared next stop's arc by ≥ `STOP_ID_LAG_MARGIN_M` (30 m, in `config.js`), `feedStats._markerStats.stopIdLag` increments — episode-gated via `marker._stopIdLagRecorded`, cleared in `updateExistingMarker`'s stopId-change block when the feed's `stopId` actually advances. STOPPED_AT cases are excluded (handled by `stoppedAtMisfire` and `declaredStopClamp`). The counter was originally pure observability; the behavior change predicated on it shipped in 2026-05-26 as the `_effectiveNextStopId` override + `getScheduledArrivals` past-target guard (next bullet).
- **GPS-inferred next-stop override (PRs #222 + #224 + #229, 2026-05-26)** — closes the "marker visibly past stop while popup says approaching that stop" complaint without re-introducing the strict clamp. Two consumers:
  - **Vehicle popup label** (`updatePopup` via `_effectiveNextStopId(marker)`): when a marker has moved past its declared next stop's arc by ≥ `STOP_ID_LAG_MARGIN_M`, the popup label and the recomputed ETA both target the first stop ahead of the marker in trip sequence — not the stale feed-declared stop.
  - **Station-popup arrivals** (`getScheduledArrivals` GPS-past-target guard): for the same threshold, a vehicle whose snap arc has moved past the target stop is dropped from that stop's arrivals (and its tripId is marked `coveredTripIds.add` so the GTFS-only loop at the bottom doesn't re-append the stale prediction). Without this guard the two popups disagreed about the same vehicle.
  - **Critical speed gate (PR #229)**: both consumers also require `smoothedSpeed >= STATIONARY_SPEED_MPS` (0.5 m/s). A stopped 3-car LA Metro train (~82 m long) reports a GPS antenna position ~25-40 m past the platform centroid (mid-car antenna), clearing the 30 m threshold even when the train is sitting at the station. Without the speed gate the override would flip the popup label / drop the arrivals while the rider can clearly see the train at the platform. With the gate, both behaviors only fire when the train is genuinely moving past the stop.
  - All other gates (no stopId, STOPPED_AT, no snap, missing route/dir/cache, stop not in cache, sub-threshold overshoot, end-of-trip) fall through to the declared `stopId` — every fall-through is "trust the feed". The override fires only when conditions positively indicate a real mismatch.
- **Feed-data correctness gates (2026-05-26)** — three rider-facing accuracy fixes the triple-pass audit surfaced: (1) `js/api.js` `processAndUpdate` rejects frames timestamped further than `FUTURE_TS_GRACE_MS` (5 s) in the future — without the gate, a future timestamp passes `Number.isFinite()` and breaks every downstream `now - ts` age check (collapses to 0 = "fresh"), letting a phantom train DR-extrapolate forward. Tracked via the new `futureTs` drop counter. (2) `js/tripUpdates.js` `processUpdate` early-returns when `trip.scheduleRelationship === 'CANCELED'` so canceled trips never populate `masterArrivalsData` — riders no longer see ETAs for trains that aren't running. (3) Inside the per-stop loop, `stu.scheduleRelationship === 'SKIPPED'` causes that single stop to be omitted while sibling stops on the same trip keep their pills — a skipped stop must never appear in the arrivals list. All three are silent in the rider UI; the only difference is the *absence* of obviously-wrong data.
- **vehicleNoArrivalMatch counter (2026-05-26)** — reverse of `ghostArrivals`. Fires in `getVehicleEtaSecs` when a live IN_TRANSIT_TO marker has a finite `stopId`, the trip_updates feed has predictions for OTHER vehicles at that stop, but none matches THIS vehicle's `vehicle_id` or `trip_id`. Sustained non-zero indicates trip_updates lost the prediction for an active vehicle and the popup will silently fall back to a schedule-based ETA. Episode-gated via `marker._noArrivalMatchRecorded`, cleared on stopId advance. STOPPED_AT excluded (boarding / misfire detectors own that window).
- **Scheduled feed-reliability audit (2026-05-26)** — `.github/workflows/feed-reliability.yml` runs `scripts/audit-feeds.js` against the live Metro WS feeds twice a week (Wed mid-day Pacific, Fri PM peak Pacific) and uploads the JSON report as a 30-day artifact. The per-field coverage table is also surfaced in `$GITHUB_STEP_SUMMARY` so reviewers see the top-line `nonNull` percentages on the run page without downloading. **This is the source of truth for "does Metro actually populate field X?"** — every future audit that proposes capturing an optional GTFS-RT field (`occupancyStatus`, `arrival.uncertainty`, `tripUpdate.delay`, `position.bearing`, etc.) must consult the latest report's `vehicleFields` / `stuFields` block before committing to the work. Decision rule: ≥30 % nonNull → wire it up; 5–30 % → document partial coverage; <5 % → skip. Manual fresh capture: Actions → feed-reliability → Run workflow (default 20 min, accepts `--duration` overrides). The CLI also runs locally: `node scripts/audit-feeds.js --duration=30m --out=/tmp/r.json`. **First-run findings (2026-05-26)**: `occupancyStatus` 0%, `arrival.uncertainty` 4% (and only the constant sentinel 300/301), `tripUpdate.delay` 0%, `position.bearing` 44% but dominated by 0°/180°/270° sentinels — all four "Tier A unused fields" identified in the prior spec-grounded audit are skip-worthy. `stopTimeUpdate.scheduleRelationship === 'SKIPPED'` fires at 6% rate (the just-shipped gate is doing real work). `trip.scheduleRelationship === 'CANCELED'` at 1.8% rate. `trip.startDate` 100%, `trip.startTime` 97% — both reliable, and confirm next-day tripIds appear in the feed mid-day (25% of trip_updates carry tomorrow's startDate hours before rollover).
- **Cross-midnight trip preservation (2026-05-26)** — `js/serviceDate.js` `_preserveActiveTrips(oldTrips, newTrips, markers)` is invoked from `_reloadGtfsData` in `main.js` during the midnight service-date rollover. For any tripId still referenced by an active vehicle marker that exists in the OLD `masterTripsData` but NOT in the freshly-fetched JSON, the old entry is merged into the new data before the swap. Owl trips that started yesterday and are still physically on the map at 00:01 keep their static context (terminus, stop sequence, `isLast` pill) until they actually terminate, instead of falling back to route-cache-only data immediately. Safety: the feed-reliability audit confirmed tripIds are NOT recycled across service dates (each day's trips have unique integer IDs in Metro's database), so preserving by tripId never silently masks a same-id-different-trip entry. Pure-function helper exported for testing; `tests/serviceDate.test.js` covers the active/inactive matrix, double-presence safety, null/missing tripIds, and the numeric-tripId String-cast defensive path.
- **Synthetic schedule-based vehicleIds filtered from `scanGhostArrivals` (2026-05-26)** — Metro's trip_updates feed publishes schedule-derived predictions for trips that haven't been assigned a live vehicle yet, using vehicleIds of the form `block_<N>_schedBasedVehicle`. The first feed-reliability audit captured 1,484 such entries in a 20-minute window. They are NOT divergence by design — the genuine-ghost signal was being swamped. `js/feedStats.js scanGhostArrivals` now skips any vehicleId ending in `_schedBasedVehicle` (suffix match for forward-compat with any future block-naming changes that keep the suffix convention).
- **`rebuild-gtfs.yml` issue-fallback (PR #217, 2026-05-26)** — the weekly Mon 09:00 UTC auto-rebuild silently failed for two weeks because `peter-evans/create-pull-request@v6` was being blocked (most likely the repo-level "Allow GitHub Actions to create and approve pull requests" setting is off; the action returns HTTP 403 and the workflow logs the error but no PR appears). Trip coverage drifted to 67% before the first `feed-reliability` audit caught it. The workflow now has an `if: failure() && steps.diff.outputs.changed == 'true'` fallback that files an issue under label `gtfs-rebuild-failure` (dedup'd by title) with a direct link to the failing run and manual-rebuild commands. The fallback was introduced AFTER the underlying drift had been fixed manually via PR #216; if the repo setting was the cause and is now enabled, the next Monday's run should produce a PR directly and neither the fallback nor manual intervention will be needed.
- **localStorage feedStats ring (2026-05-26)** — each `_report()` tick with activity appends one snapshot to `localStorage.feedStatsRing` (max `FEED_STATS_RING_MAX = 1440` entries = 24 h). Entry shape: `{ t: unixSec, feeds: { [shortName]: { rcv, acc, drops:{…}, cadence } }, markers: { …full _markerStats snapshot incl. zeros }, ghosts }`. Inspect from the console: `JSON.parse(localStorage.feedStatsRing)`. Helpers in `js/feedStats.js`: `readFeedStatsRing()`, `clearFeedStatsRing()`, `FEED_STATS_RING_KEY`. Quota / parse errors are swallowed — the ring is best-effort observability and never crashes the report tick. Silent intervals (no feed traffic, no marker counters, no ghosts) are skipped so the ring isn't padded with zero rows. The headless harness (`scripts/live-accuracy-headless.js`) clears the ring before the in-page accuracy harness starts, then at end-of-run reads it via `page.evaluate` and appends a single tagged row at the tail of the JSONL artifact (detect via `row.__kind === 'feedStatsRing'`); `summary.json.meta.feedStatsEntries` records the entry count.
- **`isEffectivelyStopped(marker)` is the canonical "really stopped?" predicate** — combines `isStoppedAt(currentStatus)` AND `!marker.properties._misfireOverride` so a STOPPED_AT misfire returns false. Used by `getSecondsToNextStop` / `getVehicleEtaSecs` / `getBoardingDepSecs` (so vehicle-popup ETAs and station-popup ETAs agree when a misfire is in flight), `isAtTerminus` / `_isAtEndOfLine` / `applyOriginVisibility` (so a misfiring vehicle doesn't get the terminus rotation lock, end-of-line fade, or origin-hide treatment), and the declared-stop clamp via the `isMisfire` parameter. Raw `isStoppedAt(currentStatus)` is reserved for the few sites that DO want to react to the literal feed status — e.g. `getPopupHTML`'s label cascade in `ui.js` (the rider sees "At stop" because the feed said so; we don't second-guess the displayed text even when we suspect it's wrong).
- **ID String-cast at the feed boundary** — `js/api.js` String-casts every feed-derived ID (`vehicle_id`, `trip_id`, `stopId`, `route_code`) before placing them on `feature.properties`. Downstream code does strict-equality lookups (e.g. `arrivals.find(a => a.vehicleId === vehicle_id)`), and the trip_updates side (`tripUpdates.js:200-201`) also String-casts on its side — a number-vs-string mismatch would silently drop cross-feed matches. The most visible failure mode is the bus/rail dispatch: `isBusRoute(routeCode)` does `routeCode === '910'`; a numeric `910` would route the whole bus fleet through rail physics with no log. Whenever you add a new feed-derived ID, cast at the api.js boundary, not at every reader.
- **`_openVehiclePopups` counter & marker-remove contract** — `markers.js` tracks open vehicle popups in this counter (incremented in `popup.on('open')`, decremented in `popup.on('close')`) so the two per-second `setVisibleInterval` ticks for popup-age refresh can short-circuit on `=== 0`. **MapLibre's `marker.remove()` does not reliably fire 'close' on an open popup**, so every call site that removes a marker MUST call `marker.getPopup()?.remove()` first — without it the counter drifts upward across multi-hour sessions and the refresh ticks run perpetually. Four such sites today: `createNewMarker` replacement of an existing key, in-flight fade cancel in `createNewMarker`, and the two `_fadeOutAndRemove` paths. The cold-start glide (`animateMarker`) uses a callback pattern (`marker._animateMarkerOnComplete`), not a returned Promise — cancellation in `updateExistingMarker`'s `animateMarkerRace` branch deletes the flag so a cancelled glide cannot fire `updateMarkerTimestamp(marker, OLD_vehicle)` after the new GPS has already been applied (which would silently regress the timestamp).
- **DR speed=0 fallback (rail)** — when GPS reports speed=0:
  - Heavy rail (B/D, 802/805) — always uses `_heavyRailScheduleSpeed` or `DR_HEAVY_RAIL_FALLBACK_MPS` (lines are 100 % grade-separated; speed=0 is always a tunnel GPS dropout).
  - Light rail — uses `isNearIntersection(lat, lng)` from `intersections.js` to decide. Near a known at-grade crossing (within `INTERSECTION_PROX_M = 50 m`) → freeze (real red-light/gate stop). Far from any crossing → fallback (tunnel or elevated GPS dropout). Crossing data lives in `data/light-rail-intersections.json` (263 points, built once via `node scripts/build-intersections.cjs` from a public Google My Maps layer; rebuild after major alignment changes).
- **Vehicle freshness tiers** — `getFreshnessTier(marker, nowSec)` in `js/freshness.js` (shared by `markers.js` and `ui.js`) is the single source of truth for per-vehicle VISUAL state. Four tiers map to (marker opacity, popup-dot color):
  - `live`    (age < 30 s)  → 1.0  / green
  - `aging`   (age < 90 s)  → 1.0  / green (no rider-visible color change — see PR #141; Metro's normal 15–35 s broadcast lag would otherwise flip the dot amber on healthy feeds)
  - `stale`   (age < 300 s) → 0.5  / gray
  - `expired` (age ≥ 300 s) → fade-out & remove
  Constants: `FRESH_LIVE_S`, `FRESH_AGING_S`, `FRESH_EXPIRE_S`, `FRESH_CHECK_INTERVAL_MS`. Decoupled from `SPIKE_BYPASS_S` (120 s, spike-rejection), `DR_MAX_SECONDS` (motion watchdog), and `VEHICLE_MARKER_TTL_S` (180 s, ETA filter) — those are algorithmic gates, not visual. The `aging` tier still exists in the data model; only its color rendering was collapsed into `live`.
- **Translation** — page source is English; the app declares `<html lang="en">` and relies on each browser's built-in translate feature (Chrome / Edge / Safari menu, iOS Safari AA menu, Android Chrome menu). The previous in-app en/es dictionary (`js/i18n.js`, `i18n/{en,es}.json`) was retired because (1) it only covered two languages, (2) it couldn't translate the LACMTA alerts feed (English-only with no `translations` field), and (3) browser-native translation handles ~100 languages AND translates alert prose alongside the rest of the page. Alert bodies are still wrapped `<p lang="en">` so screen readers and browser translators identify the source language explicitly; that wrapper is the only translation-related code remaining. (An earlier "globe" discovery button in `map.js` `CustomControls.translateBtn` was removed too — there's no JS API to trigger native translation, so the button was guesswork on top of guesswork.)

## Cross-Module Globals (`window.*`)

The app deliberately exposes shared state on `window` instead of routing every read through explicit imports. This is a conscious choice for a no-build SPA — it keeps modules small and avoids circular-import gymnastics. Treat these as the public API surface between modules; **do not refactor them away without a plan.**

| Global                                       | Owner module           | Shape                                  |
|----------------------------------------------|------------------------|----------------------------------------|
| `window.map`                                 | map.js                 | MapLibre map instance                  |
| `window.masterStopsData`                     | main.js (loads)        | Object<stopId, {lat,lon,name,…}>       |
| `window.masterTripsData`                     | main.js (loads)        | Object<tripId, {…}>                    |
| `window.masterBusRoutes`                     | main.js (loads)        | Object<routeId, {…}>                   |
| `window.masterArrivalsData`                  | tripUpdates.js         | Map<stopId, Arrival[]>                 |
| `window.masterAlertsData`                    | alerts.js              | Map<routeCode, Alert[]>                |
| `window.masterStopAlertsData`                | alerts.js              | Map<stopId, Alert[]>                   |
| `window.masterStopAccessibilityAlertsData`   | alerts.js              | Map<stopId, AccessibilityAlert[]>      |
| `window.masterBikeStations`                  | bikeshare.js           | Map<stationId, {…}>                    |
| `window.vehicleMarkers`                      | markers.js             | Object<tripId, MapLibre marker>        |
| `window.stationGroups`                       | stations.js            | Array<MergedGroup>                     |

`tripTerminusByTripId` used to live on `window` too; PR #151 removed the
mirror — production consumers (`stations.js`, `predictions.js`) now import
the named binding from `tripUpdates.js` directly. The single-access-path
invariant prevents future writers from leaving one site reading stale state.

**Debug-only hooks** (not part of the contract — present for console inspection, fine to omit when refactoring):
- `window.getCalibrationSnapshot()` and `window.getCalibrationRejectStats()` — exposed by `scheduleCalibration.js` for diagnosing per-route calibration state
- `window.__visRegistrySize` — exposed by `utils.js` for inspecting the `setVisibleInterval` registry size

### Cross-module callbacks (`window.__`)

In addition to the data globals above, `stations.js` exposes three function hooks on `window` so other modules can drive station-popup behavior **without importing `stations.js`** (which would create an init-order cycle through `main.js`). All three are set once at module load:

| Hook                                | Set by      | Called by      | Purpose                                                          |
|-------------------------------------|-------------|----------------|------------------------------------------------------------------|
| `window.__openStationByGroup`       | stations.js | bikeshare.js   | Open the station arrivals popup for a merged stop group          |
| `window.__hoverStationByGroup`      | stations.js | bikeshare.js   | Soft-preview hover (no pin) used when the user hovers a bike pin |
| `window.__closeStationIfUnpinned`   | stations.js | bikeshare.js   | Dismiss an unpinned hover-preview when the user leaves the pin   |

These are intentional inversion-of-control hooks — keep the `__` prefix and the optional-chained `?.()` call pattern so they fail silently if `stations.js` hasn't initialized yet.
